People Map Web App — Project Plan

Project goal
- Build a mobile-first multi-user web app for tracking people the user has met throughout travels and life.
- The primary interaction is an interactive 2D world map showing where people are primarily based.
- The app should also support:
  - adding and editing people;
  - viewing people in a searchable list;
  - handling people who do not yet have a based location;
  - recording where and when people were met;
  - storing contact details and free-form notes;
  - importing and exporting all user data in a portable JSON format;
  - automatic backups and restore;
  - strict separation between different authenticated users.
- Prefer conventional, well-established libraries and straightforward implementations.
- Avoid clever or unnecessarily abstract architecture.
- Keep the code easy for humans to read and review.
- Development should proceed milestone by milestone, with the coding agent stopping after each milestone for human review.

Core technology choices
- Frontend:
  - React.
  - TypeScript with strict type checking.
  - Vite.
  - MUI for UI components and mobile-first layout.
  - Leaflet for map rendering.
  - OpenStreetMap standard tiles.
- Backend:
  - Python.
  - FastAPI.
  - Pydantic for API and persistence validation.
  - Pyright in strict mode.
  - Avoid Any except where unavoidable at third-party boundaries.
  - Convert loosely typed third-party responses immediately into strongly typed internal models.
- Persistence:
  - One canonical JSON file per application user.
  - JSON is the actual canonical store, not merely an export format.
- Authentication:
  - Google OAuth.
  - Each application user receives an internal UUID.
  - Google identity is mapped to the internal UUID.
  - Application code uses only the internal UUID.
  - API endpoints derive the current user from authentication/session context.
  - Never trust a user ID supplied by the frontend for authorization.

High-level architecture
- Frontend:
  - Mobile-first React app.
  - Main screens:
    - Map.
    - People.
    - Settings.
  - Add-person action exposed prominently, preferably via a floating action button.
- Backend:
  - FastAPI routes.
  - Authentication/session layer.
  - Typed domain/API models.
  - Per-user persistence layer.
  - Backup/restore layer.
  - Import/export layer.
  - City geocoding proxy.
- Storage:
  - Conceptually:
    data/
      users/
        <internal-user-uuid>/
          people.json
          backups/
            ...
  - Exact physical layout may vary, but all reads/writes/backups must be scoped to the authenticated internal user UUID.
- Geographic data:
  - Static bundled country data.
  - Static bundled region data for supported countries.
  - External city lookup through a backend proxy.
  - Geoapify may be used for city lookup initially.
  - Geoapify API key must remain backend-only.

Person data model
- Every person has a stable UUID.
- Suggested shape:

  {
    "id": "<uuid>",
    "name": "...",
    "based_location": { ... } | null,
    "met_location": { ... } | null,
    "met_date": { ... } | null,
    "contacts": { ... },
    "notes": "..."
  }

- Name:
  - Required.
- based_location:
  - Optional in the storage schema.
  - Conceptually the primary location for the app.
  - A person with no based_location is valid.
  - People without based_location do not appear on the map.
  - They appear in a dedicated part of the People UI.
  - Do not call these people "drafts".
- met_location:
  - Optional.
  - Uses the same location structure as based_location.
- met_date:
  - Optional as a whole.
  - If present:
    - year required;
    - month required;
    - day optional.
  - Day granularity only; no time.
  - Suggested structure:

    {
      "year": 2026,
      "month": 8,
      "day": 17
    }

- notes:
  - Free-form text.
  - Optional / empty string allowed.

Location model
- Locations use a simple flexible hierarchy:
  - country;
  - optional region;
  - optional city.
- Rules:
  - country is required whenever a location object exists;
  - region is optional;
  - city is optional;
  - city may be present even if region is absent.
- Suggested structure:

  {
    "country": "Indonesia",
    "region": "East Java",
    "city": "Surabaya",
    "coordinate_cache": {
      "latitude": -7.2575,
      "longitude": 112.7521
    }
  }

- coordinate_cache:
  - Optional.
  - Explicitly treated as derived cached data.
  - Semantic source of truth is country / region / city.
  - Primarily populated for resolved city selections.
  - May be regenerated later.
  - Country/region representative coordinates normally come from bundled static geographic data.
- Do not store presentation-specific map x/y coordinates.

Location input UX
- Use three visible inputs:
  - Country.
  - Region.
  - City.
- Country:
  - Must be selected from a canonical country list.
- Region:
  - Optional.
  - For selected countries initially, provide a known region list:
    - USA.
    - UK.
    - Indonesia.
    - Australia.
    - Canada.
    - China.
  - More can be added later.
  - The schema must remain generic and allow arbitrary region strings.
  - Supporting a region selector is a UI capability, not a schema restriction.
- City:
  - Autocomplete text input.
  - Query an external geocoding/city service through the backend.
  - Constrain queries by selected country and, where possible, selected region.
  - Backend normalizes provider-specific results into an application-owned typed response schema.
  - Store selected city name and returned coordinates.
  - Allow a free-form fallback if the city service cannot resolve a location.
  - If free-form city has no coordinate cache, map rendering should fall back to region or country representative coordinates.

Contacts model
- Hybrid schema:
  - common contact methods are explicitly named fields;
  - uncommon contact methods go in an others list.
- Suggested structure:

  {
    "instagram": "...",
    "phone_number": "...",
    "whatsapp": "...",
    "email": "...",
    "others": [
      {
        "type": "telegram",
        "value": "..."
      }
    ]
  }

- All named contact fields optional.
- others defaults to an empty list.
- Keep phone_number and whatsapp separate because they are distinct contact methods even when values match.
- Avoid duplicating the same contact both in a named field and in others.
- Validation should be reasonable but not excessively strict in V1.

Canonical user JSON
- One file per application user.
- Suggested top-level shape:

  {
    "schema_version": 1,
    "revision": 42,
    "people": [...]
  }

- schema_version:
  - Explicit.
  - Used for future migrations.
- revision:
  - Integer.
  - Incremented on every successful dataset modification.
  - Used for simple optimistic concurrency protection.
- The file should be directly usable as the export format.

Concurrency and write safety
- Keep concurrency handling simple.
- Every modifying API request should include the revision it was based on.
- Backend compares it to the current dataset revision.
- If revisions differ:
  - reject with a conflict response;
  - frontend reloads current data;
  - do not attempt sophisticated automatic merging.
- All writes must:
  - be serialized per user;
  - validate before writing;
  - write to a temporary file;
  - flush/close appropriately;
  - atomically rename/replace people.json.
- Centralize all persistence mutations through one persistence layer.
- Do not allow individual endpoints to perform ad-hoc filesystem writes.

Authentication and API identity
- Real application:
  - Google OAuth.
  - Backend validates Google identity.
  - Backend maps Google stable subject identifier to an internal application UUID.
  - Backend creates an application session.
  - Prefer a secure HttpOnly session cookie.
  - API requests then look like normal calls such as GET /api/people.
  - Frontend does not need to send its own internal user UUID.
- Authorization:
  - current user is derived server-side from session/authentication context;
  - persistence paths are always derived from that internal user UUID;
  - never expose an endpoint where supplying another user UUID is enough to access their data.
- Development/testing before real OAuth:
  - retain the same CurrentUser/auth dependency boundary;
  - use a development-only fake auth implementation;
  - it may map a development-only user selector/header to configured test UUIDs;
  - ensure this mechanism is impossible to enable accidentally in production.
- Tests must include multiple fake users to verify strict isolation.

Map behavior
- Use a standard 2D projected map via Leaflet.
- Use OpenStreetMap standard tiles.
- Keep tile configuration isolated so a hosted provider can replace OSM standard tiles later without architectural changes.
- Person locations are displayed using circles rather than map-pin icons.
- Circle size is only a display choice.
- Circle radius must NOT be interpreted as geographic uncertainty or granularity.
- For locations without city coordinates:
  - country-only location -> representative country center;
  - region location -> representative region center;
  - resolved city -> city coordinate cache;
  - unresolved city -> fall back to region or country.
- Use normal Leaflet-compatible marker clustering.
- Multiple people in the same/nearby place should cluster conventionally.

Map interaction UX
- Mobile-first behavior is mandatory.
- Tap a cluster:
  - zoom toward the cluster;
  - allow clustering logic to separate markers if finer location data makes this possible;
  - simultaneously open a bottom sheet containing the people represented by that selection.
- Tap an individual person marker:
  - open the same bottom-sheet component with a one-person list.
- Bottom sheet:
  - remains associated with the visible map;
  - scrollable;
  - contains one compact full-width tile per person.
- Person tile shows:
  - name;
  - based location;
  - contact-type indicators/icons.
- Later milestone:
  - tapping a person tile opens that person's full details.
- Avoid implementing full detail navigation too early if it would make an early milestone too large.

Main mobile navigation
- Bottom navigation:
  - Map.
  - People.
  - Settings.
- Map:
  - primary/home screen.
- People:
  - searchable list of all people;
  - clear section/filter for people with no based location.
- Add person:
  - prominent floating action or equivalent.
- Person details:
  - full-screen page.
  - view details first.
  - edit action from there.
- Settings:
  - import;
  - export;
  - backup history / restore;
  - account/logout.

Person add/edit UX
- Reuse one form component for add and edit.
- Mobile-first full-screen form.
- Suggested field order:
  - Name.
  - Based location.
  - Met location.
  - Met date.
  - Contact details.
  - Notes.
- Country / region / city stacked vertically.
- Known contact fields shown explicitly.
- "Other contact" rows added dynamically.
- Notes use multiline text input.
- Inline validation.
- Missing based_location must not prevent saving.
- Save action should remain easy to reach on mobile, e.g. sticky top/bottom action area.
- In edit mode:
  - deletion is a separate destructive action near the bottom;
  - never place deletion next to Save;
  - no swipe-to-delete.

Editing, deletion, and backups
- Ordinary edits:
  - save normally;
  - no backup per field edit/save.
- Daily automatic backup:
  - on the first successful modification of a user's dataset on a given day, create that day's automatic backup.
- Delete person:
  - requires explicit confirmation;
  - confirmation names the person;
  - backend creates an immediate backup before deleting;
  - then performs an atomic write.
- Bulk destructive actions:
  - create an immediate backup first;
  - use stronger confirmation.
- No special undo system in V1.
- Recovery is through backup restore.

Backup semantics
- Keep all backups indefinitely in V1.
- No retention cleanup.
- Storage volume is expected to be small.
- Each backup should include metadata sufficient to identify:
  - timestamp;
  - reason, e.g. daily, delete_person, import, restore;
  - optionally affected person UUID where useful.
- Restore:
  - whole-dataset restore only in V1;
  - requires explicit confirmation;
  - before restoring, first back up the current state;
  - restore then atomically replaces the canonical people.json.
- No partial restore in V1.

Import/export
- Export:
  - downloads the user's canonical JSON dataset as one file;
  - filename should include the date, e.g. people-map-2026-09-05.json.
- Import default:
  - merge.
- Import validation:
  - validate the entire file before any write;
  - reject malformed data;
  - reject unsupported schema versions;
  - determine:
    - new people;
    - identical already-present people;
    - UUID conflicts.
- Merge rules:
  - imported person UUID absent locally -> add;
  - imported UUID exists and record is exactly identical -> no-op;
  - imported UUID exists but any field differs -> conflict.
- Any conflict:
  - fail the entire import;
  - make no changes;
  - do not partially import;
  - do not attempt field-level merging in V1.
- Import UX:
  - validate first;
  - show summary such as "12 new, 3 already present";
  - only apply after confirmation.
- Before applying a successful import:
  - create a backup.
- Replace-all import:
  - do not implement in the first version unless explicitly added later.
- Future versions may add richer conflict handling.

Geography data and city lookup
- Bundle static country metadata.
- Bundle static region metadata for supported selector countries.
- Static metadata should include representative coordinates.
- Use established geographic datasets or libraries rather than manually invented coordinates.
- City lookup:
  - frontend calls application backend;
  - backend calls provider such as Geoapify;
  - API key remains backend-only;
  - backend returns normalized typed city results.
- Example normalized city response:

  {
    "name": "Surabaya",
    "region": "East Java",
    "country": "Indonesia",
    "latitude": -7.25,
    "longitude": 112.75
  }

- Never send person names, contacts, or notes to the geocoding provider.
- Only geographic search text and geographic constraints should leave the application backend.

Privacy and security principles
- Treat data as private and sensitive by default.
- Data may include:
  - names;
  - phone numbers;
  - social handles;
  - approximate home locations;
  - notes.
- Requirements:
  - strict per-user isolation;
  - HTTPS in deployment;
  - no public profile URLs by default;
  - avoid analytics that capture form contents;
  - avoid unnecessary third-party transmission;
  - do not expose Geoapify API key to the frontend.
- Authentication and authorization logic should remain straightforward and auditable.

API shape
- Exact route naming can be adjusted during implementation, but keep the API small and conventional.
- Likely endpoints:
  - GET /api/people
  - POST /api/people
  - GET /api/people/{id}
  - PUT /api/people/{id}
  - DELETE /api/people/{id}
  - POST /api/imports/validate
  - POST /api/imports/apply
  - GET /api/export
  - GET /api/backups
  - POST /api/backups/{id}/restore
  - GET /api/locations/cities
- Endpoints must use authenticated CurrentUser context rather than user IDs from URL/query/body for authorization.
- Mutating requests should carry expected dataset revision where appropriate.

Frontend coupling policy
- MUI is the chosen UI library.
- Do not build a large abstraction layer merely to hide MUI.
- Instead:
  - keep application/domain logic independent of MUI;
  - keep data fetching/state hooks independent of MUI where practical;
  - create sensible application-level components such as:
    - PersonListItem;
    - LocationEditor;
    - ContactEditor;
    - PersonSheet;
    - ConfirmDeleteDialog.
- Avoid allowing MUI-specific types to leak into shared domain/data layers.
- This should keep future UI-library migration possible without making V1 over-engineered.

Testing and CI
- Backend unit tests:
  - person schema validation;
  - location validation;
  - met-date validation;
  - contact validation;
  - merge-import behavior;
  - revision conflicts;
  - backup creation;
  - restore behavior;
  - delete behavior;
  - persistence atomicity;
  - user isolation.
- Backend API tests:
  - authenticated user only accesses own dataset;
  - malformed import leaves data untouched;
  - conflicting import fails atomically;
  - city proxy normalizes provider responses.
- Frontend tests:
  - key form behavior;
  - saving person without based location;
  - people-without-location UI;
  - cluster/person selection -> bottom sheet;
  - import summary UI;
  - destructive confirmation flows.
- End-to-end tests:
  - keep small in V1;
  - key flows only:
    - sign in -> add person -> appears in list/map;
    - edit/delete person;
    - export/import round trip.
- CI should run early and continuously:
  - frontend tests;
  - backend tests;
  - TypeScript type checking;
  - Pyright strict type checking;
  - linting;
  - formatting checks where appropriate;
  - frontend production build.
- Avoid large snapshot-test suites or excessive browser-test infrastructure.

Implementation principles for the coding agent
- Favor boring, conventional solutions.
- Keep modules small and responsibilities obvious.
- Strong typing is a hard requirement, especially in Python.
- Do not use Any as an escape hatch.
- Keep third-party integrations behind narrow typed boundaries.
- Keep authorization server-derived.
- Keep persistence mutations centralized.
- Prefer explicit validation and safe failure over implicit recovery.
- Do not silently merge conflicting imported data.
- Do not optimize for hypothetical large-scale usage.
- Preserve mobile-first UX in every frontend decision.
- Do not proceed past a milestone until a human reviewer has approved it.
